## Story

As **a maintainer of the API's raw-SQL layer**,
I want **CI to fail when SQL casts a TEXT column to a stricter type, or relies on a neighbouring conjunct to make an operation safe**,
so that **a sentinel or malformed value in a TEXT column can never again turn a staff-facing read into an intermittent 500 — the whole class is caught mechanically at write time instead of surfacing months later as a "flaky test" nobody trusts.**

## Context & Evidence (verified 2026-07-22)

- **The defect was real and shipped, five times.** Casts of `submissions.questionnaire_form_id` (TEXT) to `uuid`: `respondent.service.ts` ×3 (registry list/search, respondent detail, submission-response detail) "guarded" by `col ~ <uuid regex> AND col::uuid = qf.id`; `fraud-detections.controller.ts:231` with **no guard at all**; plus `supervisor.controller.ts:144` casting `submitter_id::uuid` (prophylactic — no non-UUID writer today). All fixed in 13-34 by joining in TEXT space (`qf.id::text = s.questionnaire_form_id`).
- **The guard idiom is the actual bug.** `WHERE`/`AND` conjuncts have no defined evaluation order in SQL; Postgres may evaluate `col::uuid` on rows the regex was meant to exclude and abort the statement. **Plan-dependent** ⇒ it can pass for months and start failing when row counts or stats shift the plan ⇒ it presents as an intermittent test failure, not a bug.
- **The class is wider than `uuid` — same trap, different SQLSTATE:**
  | Written | Fails as | Realistic trigger here |
  |---|---|---|
  | `text_col::uuid` | `22P02` | sentinels (`supplemental-survey`, `self-edit`) — **already happened** |
  | `text_col::int` / `::numeric` | `22P02` | any free-text numeric answer in `raw_data` (`'12 years'`, `''`) |
  | `text_col::date` / `::timestamptz` | `22007`/`22008` | XLSForm date answers, partial dates, `'N/A'` |
  | `text_col::jsonb` | `22P02` | any hand-built JSON string column |
  | `num / other_col` | `22012` | a `WHERE other_col <> 0` conjunct does NOT protect the division |
  Every one is the same sentence: *a filter beside an operation does not order that operation*. `raw_data->>'…'` is TEXT by definition and is the project's most common source of cast targets, so the non-`uuid` variants are not hypothetical.
- **Doc-only enforcement already failed here.** The comment `// Guard UUID casts from legacy/non-UUID questionnaire_form_id values in submissions` sat directly above the broken guard and was copied to a second site. A comment that *describes* the hazard did not prevent it; four writings survived review.
- **Precedent to mirror:** 13-37 (`lint-registry-read-drift.ts`) — a pure finder fn, file allowlist with reasons, inline escape hatch, blocking step in `lint-and-build`, and a test asserting it catches *and* permits. ⚠️ **13-37 has since SHIPPED and been adversarially reviewed (12 findings, 3 High), and its as-built shape is NOT what this story described.** See the PM ruling in Dev Notes; the "mirror 13-37" instruction below was corrected on 2026-07-30 after it was found to have copied two of 13-37's review defects into this story before a line was written.

## Acceptance Criteria

1. **AC1 — Detect casts of TEXT columns to a stricter type.** Detector core at **`apps/api/src/lib/unsafe-sql-cast.ts`** with a thin CLI runner at **`apps/api/scripts/lint-unsafe-sql-cast.ts`** (exposed as a `pnpm` script), scanning **`apps/api/src/**` AND `apps/api/scripts/**`** for `<column-expression>::<type>` where the target resolves to a TEXT column and `<type>` is any of `uuid`, `int`/`integer`/`bigint`/`smallint`, `numeric`/`decimal`/`real`/`double precision`, `date`, `timestamp`/`timestamptz`, `time`, `boolean`, `json`/`jsonb`. Exits non-zero on any hit not covered by AC3. **Casts TO `text` are never flagged** (they cannot throw — and are the remedy).
   - **Layout is FORCED, not stylistic** (corrected 2026-07-30; this story previously specified a single file under `scripts/` and called it "the 13-37 convention" — it is the opposite). `apps/api/tsconfig.json:10` sets `rootDir: ./src` and `:16` includes only `src/**/*`, so **a `src` file importing from `scripts/` breaks `tsc`**, and anything left in `scripts/` is never type-checked. Logic must live in `src/lib` to be type-checked by `pnpm build` and unit-tested by the `test-api` job. Precedent: `src/lib/osv-prod-gate.ts` + `scripts/osv-prod-gate.ts`, and `src/lib/registry-read-drift.ts` + `scripts/lint-registry-read-drift.ts`.
   - **`scripts/**` is in scope** because that is where one-off backfills live — the highest-risk-per-line directory in the package. 13-37 added this root in its code review (L5) and measured it free (54 files, 0 hits).
2. **AC2 — Bound parameters are NOT flagged; `${…}` alone does NOT mean "bound parameter".** `${id}::uuid`, `$1::uuid`, `${new Date()}::timestamptz` are the safe, ubiquitous, correct usage and must pass. Only casts whose target is a **column reference** (`alias.column`, a bare known column name, **or a `${…}` whose expression is a Drizzle column object**) are candidates.
   - **This discrimination is load-bearing, and the naive reading of it is already wrong.** `form.controller.ts:276` writes `${submissions.submitterId}::uuid` — textually indistinguishable from a bound param, semantically a TEXT **column**, and a live instance of the defect (Context above). A checker that treats `${…}::T` as "param ⇒ safe" would classify this story's own best available real-world test case as PASS. That is [[pattern-ship-a-fix-that-never-fires]] inside the guard built to prevent it.
   - **The discriminator is the expression inside the interpolation**, which AC11's AST source model hands over directly: a property access rooted at a Drizzle schema import (`submissions.submitterId`) is a COLUMN; a bare identifier / call / literal (`id`, `cursorId`, `new Date()`) is a PARAM. Ambiguous cases fall through to AC3's column-name matching, then to a hit — a false positive is loud and fixable; a false negative is the bug shipping again.
3. **AC3 — TEXT-column awareness + suppression (near-zero false positives).** The checker derives the TEXT-column name set from the Drizzle schema (`apps/api/src/db/schema/**`, `text('…')` declarations) — a `uuid`-typed column cast to `uuid` is a no-op, not a hazard. Ambiguous raw-SQL aliases fall back to matching the column NAME against that set. Plus (i) a file allowlist with a one-line reason each, and (ii) an inline `// sql-cast-ok: <reason>` escape hatch; **no reason ⇒ failure**.
4. **AC4 — Flag the FALSE-GUARD idiom independently of type resolution.** Report `col <regex/LIKE/IS NOT NULL/<> ''/comparison> … AND … col::<type>` (either order, same SQL template) with its own message: *AND does not order evaluation — the filter does not protect the cast*. This must fire even when the column's type cannot be resolved, because it is the exact shape that shipped. Same treatment for a division whose only protection is a sibling `<> 0` conjunct (`22012`).
5. **AC5 — `raw_data->>'…'` targets count as TEXT.** A JSONB `->>` extraction is TEXT by definition; casting it (`(s.raw_data->>'age')::int`) is **not a future instance of this class — it is the dominant CURRENT one: 53 live sites across 4 files** (Context above). Flag it, and point at the safe forms in the message. Because this rule alone determines the size of AC10's triage, it must be implemented and measured **before** the exotic variants, not after.
6. **AC6 — Wired into CI as a blocking step, ABOVE `Lint`.** Runs in the deploy-gating `lint-and-build` job (`.github/workflows/ci-cd.yml`) as its own named step, and locally via `pnpm --filter @oslsr/api lint:sql-cast`, folded into the package `lint` chain. (Scripts sit outside tsconfig — RUN it; don't trust `tsc`.)
   - **⚠️ ORDER IS AN ACCEPTANCE CRITERION, not a preference.** The named step MUST appear before the `Lint` step. 13-37 shipped this exact wiring with the step *after* `Lint` and the named step **could never execute**: `pnpm lint` → turbo → the api `lint` chain already runs the guard, so a real hit reddens `Lint` and aborts the job first. Found as High finding **H1** in the 13-37 code review; fixed by moving the step above `Lint` (`ci-cd.yml:149-153` today). **AC6 as originally drafted here reproduced that defect verbatim** — both-places wiring, no ordering constraint, Task 4 saying "next to the 13-37 guard" (which at drafting time meant *below* `Lint`).
   - **Doc-only enforcement of the ordering is not acceptable in this story of all stories.** 13-37's fix was a `⚠️ ORDER MATTERS` comment — i.e. exactly the "a comment that describes the hazard" mechanism whose failure is this story's founding evidence (Context, "Doc-only enforcement already failed here"). Ship a **test** that reads `.github/workflows/ci-cd.yml` and asserts every custom-guard step's index within `lint-and-build` is less than the `Lint` step's index. No YAML dependency needed — comparing line indices of `- name:` entries is sufficient. The assertion covers the 13-37 step too, so it can never silently regress either.
7. **AC7 — Actionable failure message with the remedy per type.** `file:line` + snippet + WHY (SQLSTATE, plan-dependent 500, the 13-34 incident) + the fix:
   - joins → **cast the typed side to text** (`uuid_col::text = text_col`);
   - value use → **order the evaluation explicitly** with `CASE WHEN <test> THEN <cast> END`, or use a total function (`NULLIF`, `to_date(…)` with validation, `pg_input_is_valid(…, 'uuid')` on PG16+);
   - division → `NULLIF(divisor, 0)`.
   Plus the escape-hatch syntax.
8. **AC8 — Tests prove it catches and permits.** In `apps/api/src/lib/__tests__/unsafe-sql-cast.test.ts` (beside the detector — **not** `src/__tests__/`, corrected 2026-07-30). Fixtures covering: `s.questionnaire_form_id::uuid` FAILS · `(raw_data->>'age')::int` FAILS · `col ~ regex AND col::uuid` FAILS (even with types unresolvable) · `a / b` with a sibling `b <> 0` FAILS · `${id}::uuid` PASSES · `qf.id::text = s.questionnaire_form_id` PASSES · `CASE WHEN … THEN col::int END` PASSES · `NULLIF(b,0)` PASSES · allow-listed file PASSES · escape hatch with reason PASSES, without reason FAILS. **AC8 is necessary but NOT sufficient — see AC12.**
9. **AC9 — A runtime canary, not just a linter.** One integration test proves the *behaviour* the linter protects: insert a submission carrying the REAL `'supplemental-survey'` sentinel, then exercise the registry reads (`listRespondents` search + `getRespondentDetail`) and the fraud-detection detail read — all must return normally. (The registry half exists from 13-34 in `respondent-search-db-smoke.integration.test.ts`; extend to the fraud-detection read.) A linter can be escape-hatched; the canary cannot.
10. **AC10 — Green on the current tree, from a MEASURED baseline (rewritten 2026-07-30 — "zero hits" was false).** The tree carries ≥55 hits of this class today (Context). The exit condition is therefore *every hit triaged with a recorded disposition*, not *no hits found*:
    1. **Publish the measured baseline** in the Dev Agent Record — total hits, per-file counts, per-rule counts — *before* any fix or allow-list. This is the number a reviewer checks the triage against.
    2. **Every hit gets exactly one disposition, recorded:** `FIXED` (with the remedy applied, per AC7) · `ALLOW-LISTED` (with a one-line reason naming why the column cannot hold a bad value) · `DEFERRED` (with a named follow-up story). **Widening a pattern, narrowing the type list, or dropping a rule to make the tree green is a story failure** — that is a silent re-scope disguised as a passing build.
    3. **The fix-vs-allow-list call is decided by production DATA, not by reading code.** Before dispositioning the 53 `->>`-cast sites, run one read-only prod query counting values that cannot parse — e.g. rows where `raw_data->>'dob'` is non-NULL and fails a `date` parse (`pg_input_is_valid` on PG16+, else a regex + `to_date` probe on a bounded sample). A non-zero count means those sites are **live 500s on the public `/insights` page and staff analytics**, which changes their disposition to `FIXED` and this story's urgency; zero means `ALLOW-LISTED` with that count as the stated reason, plus a note that the reason expires if a new writer appears. Record the query and its result. ([[pattern-ship-a-fix-that-never-fires]]: a disposition asserted from source alone proves nothing about prod.)
    4. **`form.controller.ts:276` and `:325` are `FIXED`, not allow-listed** — they are the same unguarded TEXT→uuid shape 13-34 remediated two files away, and the remedy is already written down at `supervisor.controller.ts:144` (compare in TEXT space: `IN (SELECT id::text FROM users WHERE …)`). Leaving them suppressed while shipping a guard against them is not defensible.
    5. Full API suite + `tsc --noEmit` + eslint clean; CI `lint-and-build` green with the new step, **in the AC6 position**.
11. **AC11 — Absorb the shared CI-guard toolkit (PM ruling, 2026-07-30 — see Dev Notes).** This story does **not** copy 13-37's plumbing a second time. It extracts it, and is its first second consumer.
    - **(a) Extract to `apps/api/src/lib/ci-guard/`** (type-checked + unit-tested, per AC1's `rootDir` constraint), consumed by thin `apps/api/scripts/lint-*.ts` CLIs. Minimum surface, all of it already built and reviewed in `src/lib/registry-read-drift.ts` + `scripts/lint-registry-read-drift.ts`: the multi-root file walk with the exclusion sets (`__tests__`/`test`/`tests`/`node_modules`/`dist`; `.test.ts`/`.spec.ts`/`.d.ts`) · path-rule matching with Windows normalization (`PathRule { pattern, reason }`) · the allowlist-with-reason mechanism · the inline escape hatch (token-parameterised, `MIN_REASON_CHARS`, comment-position check, statement-scoped lookup, and `suppressedRule` reporting) · the hit record (`file`/`line`/`rule`/`snippet`/`why`) with stable `file`-then-`line` sort · the failure-message skeleton (header → blocks → FIX → GENUINE EXCEPTION) parameterised by remediation text · and the runner factory owning I/O and exit codes.
    - **(b) The toolkit's source model is AST-backed, not regex-over-blanked-text.** It exposes the SQL tagged templates of a file as nodes — each with its span, its literal chunks and its **interpolation expressions** — via `ts.createSourceFile` (`typescript@^5.4.5` is already an `apps/api` devDependency, `package.json:102`; no new dep). Rules run over template nodes, not whole files. This replaces `maskComments` (whose documented KNOWN LIMIT — a regex literal containing `//` opens a phantom comment and over-masks, a false *negative* — disappears, since comments are simply not template nodes) and replaces the `templateWindow` "scan to the next backtick, capped at 800/1500 chars" heuristic with real statement boundaries. **13-41 needs this far more than 13-37 did:** AC2's param-vs-column call *is* an interpolation-expression question, AC3 must parse 28 Drizzle schema files for `text('…')` declarations (a TS parse either way), and AC4 must decide "same statement" for a filter and a cast — that is a template-node boundary, not a character count.
    - **(c) Repoint 13-37 onto the toolkit under a strict equivalence gate — repoint, do not rewrite.** Its 46 tests must stay green **unmodified except for import paths**, and the guard must still measure **344 files / 0 hits** on the tree. If the repoint cannot clear that gate inside this story, **13-37 keeps its existing regex path and the toolkit ships with 13-41 as its only consumer** — a smaller win, not a blocked story. Do not weaken 13-37's tests to make the repoint pass; that inverts the gate.
12. **AC12 — Prove the rules against the REAL tree, not only against fixtures.** AC8's fixtures encode only the evasions their author imagined; 13-37 shipped rules that matched `LEFT JOIN` and `LEFT JOIN LATERAL` alone and were blind to `JOIN`, `INNER JOIN`, `LEFT OUTER JOIN`, the comma join and `CROSS JOIN LATERAL` — **every one of which was already in this codebase** (`survey-analytics.service.ts:1674-1675`). Three High review findings, invisible to 30 green tests. This story's AC8 has the identical blind spot, so the antidote is an AC, not advice:
    - **(a) Enumerate the syntactic variants per rule before implementing it** and record the list (cast spellings incl. whitespace/newlines/comments between operand and `::`, `CAST(x AS t)` as well as `x::t`, `->>` vs `->>'k'` vs `#>>'{a,b}'`, quoted vs unquoted identifiers, alias-qualified vs bare, and — for AC4 — each guard spelling `~`/`LIKE`/`SIMILAR TO`/`IS NOT NULL`/`<> ''`/`IN (…)`/`BETWEEN` on either side of the `AND`).
    - **(b) Measure each variant against the real tree**, and record hit deltas. A variant that costs 0 new false positives is added; one that costs many is scoped (with the measurement as the reason) rather than dropped silently.
    - **(c) Regression-lock against the REAL canonical artifacts, not lookalikes.** At minimum: a test importing the **real Drizzle schema** asserting `submissions.submitter_id` and `submissions.questionnaire_form_id` are in the derived TEXT set (so renaming a column or flipping it to `uuid()` cannot silently disarm AC3), and a test planting the **verbatim** current text of `form.controller.ts:276` in a non-allowlisted fixture path asserting it is caught. 13-37's equivalent (M1) exists because hand-written lookalikes had silently diverged from the artifact they were meant to pin.
    - **(d) RED-verify on the real filesystem.** Plant canaries in the *missed* spellings, confirm the runner exits 1 naming each `file:line`, confirm a reason-carrying escape hatch suppresses exactly one, then delete them and re-verify the tree and `git status` are clean.

## Dev Notes

### ⚖️ PM RULING 2026-07-30 (John/PM) — 13-41 ABSORBS the toolkit extraction and the AST decision

**Trigger:** the 13-37 adversarial code review (12 findings: 3 High, 4 Med, 5 Low). **Ruling: YES on both.** 13-41 extracts a shared CI-guard toolkit (AC11) instead of copying 13-37's plumbing, and the toolkit's source model is AST-backed (AC11b) rather than regex-over-comment-blanked-text.

**Why the second instance is the right time here, not the third.** The usual argument for waiting is that one example does not reveal the seam. That argument does not apply, because the seam is not being guessed — it was **built once and adversarially reviewed once**, and the review's findings landed almost entirely in the layer that would be copied: H1 (CI step ordering), H2/H3 (matcher breadth), M2 (escape-hatch scope), M3 (`suppressedRule` reporting), L1 (comment-position check), L4 (exclusion sets), L5 (scan roots). Copying that layer copies its defect surface at exactly the moment we have the defect list.

**And the copying already happened, before a line of code was written.** This story said "mirror 13-37" and thereby inherited three of 13-37's own defects textually:
1. **AC6/Task 4 reproduced H1** — guard in the `lint` chain *and* as a named step, with no ordering constraint, "next to the 13-37 guard" (which at drafting time meant below `Lint`, i.e. unreachable).
2. **Task 1 / Task 5 / Project Structure Notes reproduced the pre-M4 layout** — pure core under `scripts/`, test under `src/__tests__/` — which `apps/api/tsconfig.json:10` (`rootDir: ./src`) forbids, and which 13-37's review had to correct as finding M4.
3. **AC8 reproduced the fixture blind spot** that produced H2 and H3.
That is three inherited defects from one instruction. It is the empirical answer to "is copying cheap here?" — measured, not asserted.

**Where it lives: `apps/api/src/lib/ci-guard/`.** Rejected alternatives:
- *`packages/utils` or a new `packages/ci-guard` workspace.* Both guards are API-only, and `apps/web/package.json:23` depends on `@oslsr/utils` — putting a `node:fs` file-walker there drags it into the web build graph for zero cross-app benefit, and a new package adds a build edge and a version to maintain for two consumers in one app.
- *`apps/api/scripts/shared/`.* Fails AC1's constraint: `scripts/` is outside tsconfig, so the shared layer would be neither type-checked nor unit-tested — the exact defect 13-37's M4 corrected.
- *Extract in a standalone refactor story (13-41a) first.* Rejected: a seam extracted with only one consumer is a guess. Extracting **inside** 13-41 means every generic decision is validated by two live consumers in the same pass, and the equivalence gate (AC11c) makes the regression risk explicit and bounded.
- *Copy now, extract at the third guard (rule of three).* Rejected on the evidence above. Note the rule-of-three count is also already ambiguous: `src/lib/osv-prod-gate.ts` + `scripts/osv-prod-gate.ts` is a third instance of the **core/runner split convention** — but it consumes JSON, not source files (no walk, no allowlist, no escape hatch), so it shares the *convention* and none of the *plumbing*. **The split convention needs no extraction (it is already a convention); the source-scanning plumbing is at instance two and is what AC11 extracts.** Keeping those two tiers distinct is the whole ruling.

**Why AST, and why the drafted rationale against it does not hold for this story.** The "Approach" section below argued (inheriting 13-37's reasoning) that an AST rule "would re-assemble and regex the quasis anyway". That is true for 13-37, whose rules are pure text patterns over SQL. It is **false for 13-41**, whose three hardest requirements are all structural, not textual:
- **AC2** must tell `${submissions.submitterId}::uuid` (a TEXT **column** — a live defect at `form.controller.ts:276`) from `${cursorId}::uuid` (a bound param — safe, and everywhere: `marketplace.service.ts:123,133,250`, `personal-stats.service.ts:315,378,540`, `respondent.service.ts:314,378`). Both are `${…}::uuid` in flat text. The discriminator is the interpolation's **expression**, which only a parse hands you reliably across multi-line templates.
- **AC3** must read `text('…')` declarations out of 28 Drizzle schema files. That is a TypeScript parse whichever way it is written — doing it with a regex and the rest with an AST means maintaining two source models.
- **AC4** must decide that a filter and a cast are in the **same statement**. 13-37 approximates this with `templateWindow` — scan forward to the next backtick, capped at 800/1500 chars. That is a heuristic standing in for a node boundary.
Cost: the 13-37 review measured the AST path at **185ms → 1212ms across 344 files, 0 parse failures, and identical detections (6 vs 6, zero disagreements)**. A ~1s addition to a job that already runs eslint, `tsc` and a full Vite+tsc build is not a cost worth trading correctness for; rejecting AST on performance grounds is not a credible position. `typescript@^5.4.5` is already an `apps/api` devDependency (`package.json:102`) — **no new dependency**.

**What the ruling does NOT do.** It does not rewrite 13-37's detector. AC11(c) *repoints* it under an equivalence gate (46 tests green on import-path changes only; still 344 files / 0 hits) with an explicit fallback: if the gate cannot be cleared in this story, 13-37 keeps its regex path and the toolkit ships with one consumer. Extraction must not become a licence to re-litigate a just-reviewed detector.

### Why WIDE, decided up front
Scoping this to `::uuid` would guard the instance we happened to be burned by and leave `(raw_data->>'x')::int` — a more likely future instance, since `->>` is TEXT by definition and the codebase reads `raw_data` everywhere — to be rediscovered in production. **The checker's cost is in the plumbing** (schema parse, template scanning, allowlist, escape hatch, CI wiring, tests), which is identical either way; the type list is a constant and the false-guard matcher is one more regex. Narrow scope would buy nothing and defer the same work. (Awwal, 2026-07-22: *"It is of no use to have foresight and not apply it. The volume of work does not reduce either way."*)

### Approach — a standalone script, with an AST source model (amended 2026-07-30)
- **Still a standalone `tsx` script, not an eslint rule.** An eslint rule would tie the check to eslint's lifecycle and config, make it awkward to run as its own named CI step (AC6), and make it hard to unit-test the finder in isolation. That part of the original reasoning stands.
- **But the detector parses instead of regexing whole files.** ⚠️ The original bullet here — "an AST rule would re-assemble and regex the quasis anyway" — was inherited from 13-37 and **does not survive contact with this story's ACs**: AC2's param-vs-column call, AC3's schema parse and AC4's same-statement boundary are all structural questions. See the PM ruling above for the full argument and the measured cost. "Script, not eslint rule" and "text scan, not parse" were always two separate decisions; only the first was actually load-bearing.
- **Credibility beats coverage.** A guard that fires on `${id}::uuid` gets escape-hatched reflexively and then protects nothing. AC2/AC3 (param exclusion + schema-derived TEXT set) are what make the wide scope tolerable; if a variant proves noisy in practice, narrow THAT variant with a documented reason rather than widening the escape hatch. **The converse also binds:** a guard that misses `${submissions.submitterId}::uuid` because it assumed `${…}` means "param" has coverage that reads well and protects nothing. AC12 exists to keep both failure directions measured rather than assumed.

### Why AC9 exists
A linter guards the *shape*; the canary guards the *behaviour*. 13-34's lesson ([[pattern-flaky-test-hiding-a-prod-bug]]) is that this class hides behind plan-dependence — if someone escape-hatches the linter with a plausible reason, the canary still fails loudly. Note the inverse project lesson ([[pattern-ship-a-fix-that-never-fires]]): a guard that never executes against real data proves nothing, so the canary uses the REAL sentinel string, not an invented one.
